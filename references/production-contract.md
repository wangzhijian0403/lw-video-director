# LW 整片制作协议 · v0.3 草案

## 目标与范围

用户真正要的只有两件事：**画面足够专业、流畅、好看**；**尽量一次输入主题/素材，就能自动交付一条可发布前审核的完整视频**。把“生成五个静音组件 MP4”与“完成有口播、字幕、场景变化的整片”严格区分。Skill 负责指挥、资产选型、制作与审片；Visual Studio 负责实际可验证的渲染能力。**流程指令不能替代未实现的执行引擎。**

## 默认创作约定

- 抖音主题未指定画幅时，按 **9:16** 设计；科技科普默认 45–60 秒，字幕简体中文，目标 1080×1920/30fps/H.264 MP4/AAC；如果用户明确要求横屏、3:4、长片或无字幕，以用户为准。
- 当前 0.2 渲染器只验证 1280×720、30fps 的**单组件无音轨** MP4。默认的9:16目标在竖屏 Composition 实装及真实验收前属于 **blocked**，不得借纯粹裁剪/拉伸冒充支持。
- 默认使用 LW 已核验的原创组件；外部库只选已合法取得、具实际可运行源码与渲染证据的条目。Motion Prompt MP-001 可尝试，FredTalk metadata-only 不可作为执行引擎。
- 主题、镜头风格和音乐选择优先匹配受众、叙事、情绪，不为了炫技而堆叠效果；文案中具体事实必须核对来源。
- 只要求用户提供其独有、无法自动取得的素材或授权；其他常规决策由系统执行并记录，最后交用户审片。

## 逐阶段执行，不得跳步伪造

### A. 输入与环境检查

建立独立项目目录 `projects/<slug>/`，原片放 `source/` 只读，导出放 `renders/`，文案/镜头/许可/QA 在 `metadata/`。检查 Python、Node、Remotion、浏览器/3D、FFmpeg、语音服务、素材权利。用户只给主题时，用原创脚本、原创动态图形和授权的 TTS/录音；缺合法 TTS 方案要列出唯一阻塞，不冒充生成音频。

### B. 文案与口播

明确主题、目标人群、核心论点，先写钩子→解释→论据→结论。根据实际录音/配音产生 **带时间码** 的分句/逐词转写。不能仅以字数、平均语速猜测音频时间；实际以解码音频和对齐结果为准。技术事实/数字要核对，未核对的数据标为示例。

### C. 分镜与视觉编排

镜头计划以 `episode.json` 为唯一数据源，按帧记录 `startFrame`、`durationFrames`、`componentId`、`library`、`props`、字幕与配音片段、转场/视觉交接、素材与许可。一个场景必须回答“口播讲什么、看见什么、为什么这个画面比一页大字好”。

选择组件前必须读取当前 `visual-studio/src/catalog/manifest.json`、`quality.json`、`external/catalog.json` 的**真实可用状态**；只有渲染通过的组件可直接选择。类别不足时可为本期原创新场景，但需实际渲染验证；不以同一动效机械重复全片。

### C2. LW Asset Engine 素材解析与调用

读取 [素材引擎规范](asset-engine.md)。先导入口播对应的结构化语义，按镜头职责、情绪与主视觉推荐素材；再核验来源、授权范围与哈希，编译 assetId 到项目时间轴。在线候选默认只参考，未获授权不下载/使用；允许下载、允许改编和可执行互不替代。所有媒体、字体、MG、配音、音乐和音效使用同一台账。缺失素材时明确记录原创 MG 替代；最终强制生成使用清单和版权报告。

### D. 声画制作与同步

配音为主轨，BGM/SFX 只用获授权的素材。按对齐的时间码布置字幕，字幕要控制字数、停留和安全区域。场景应在真实句意转折处衔接，不能只把若干独立 MP4 片段首尾相连。入场/停留/退场和跨场景镜头状态按场景关系设计。若没有能实际运行的整片 Composition/混音/字幕模块，不进入“成片已完成”状态。

### E. 真实渲染与两级 QA

- **技术检查**：编码、音轨、分辨率、帧率、时长、是否有黑/重复帧、渲染异常、字幕区域、首尾空白、音频峰值、音视频漂移、版权台账。音频响度与峰值只作建议起点，不把平台偏好冒充强制标准。
- **视觉检查**：人工或具备真实视频观看能力的审片流程查看全片节奏、主视觉、运镜自然度、文字可读性、材质、光影、动画停留、场景转场。文字正确不等于画面合格，`npm test` 通过不等于视觉通过。
- **返修**：记录 `shotId`、时间码、问题、原因为何、计划改动，保护未受影响片段，重新渲染后检验接缝与音频。

## 交付合同

只有以下交付物同时存在且经过本次运行核验，才可告知用户“整片完成”：

1. `final.mp4`：真实可解码、包含要求的画面、配音/音效及字幕，符合目标画幅；
2. `episode.json`：可编辑的整期配置、镜头时间线、素材来源；
3. `narration.*` 与 `subtitles.srt` 或对应真实音频/字幕索引；
4. `qa.json`：技术与审片结论、已知问题、真实测试环境；
5. `assets.json`：媒体、字体、BGM、外部源码的出处、许可和是否可发布。

若尚缺 TTS、分镜时间轴、整片渲染器或字幕模块，输出项目目前的 **draft / preflight-blocked / render-ready / rendered / reviewed** 状态，不声称全自动完成。v0.2 单组件渲染仍独立；新增 Asset Engine FFmpeg/PyAV 适配器已做本机私有整片技术验证，见素材引擎规范。它不替代尚未验收的原生 Remotion 整片 Composition、通用 ASR 或主题自动创作。

## 预检用法

```powershell
python scripts/episode_preflight.py templates/episode-manifest.example.json --phase plan
python scripts/episode_preflight.py templates/episode-manifest.example.json --phase render
```

计划态应能识别合理的镜头表；渲染态对例子中的缺口必须报错。只有实际整片引擎经过测试并在 `visual-studio/production/capabilities.json` 记录已验证能力后，才能将渲染态门禁打开。不要手动写假能力来绕过门禁。


对 `schemaVersion: asset-engine/1`，预检调用同一素材编译器；render 门禁核对本项目真实 QA、成片哈希、输出规格及当前适配器源码哈希，不接受只改 capability 布尔值。其他旧 manifest 继续遵守原门禁。
